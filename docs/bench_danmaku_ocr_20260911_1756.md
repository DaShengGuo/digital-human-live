# 弹幕读取方案实测: 本地 OCR vs 本地通用视觉模型 (VLM)

- 生成时间: 2026-09-11 17:55:02
- 脚本: `scripts/bench_danmaku_ocr.py` (可用 `D:\Python39\python.exe` 复跑)
- 素材: 抖音手机截图副本, `data/bench_danmaku/` (原始文件未改动)

## 0. 结论速览

**推荐 OCR（rapidocr 3.9.2，CPU）。VLM（qwen2.5vl:7b）在 8G 卡上直接排除。**

| 维度 | OCR（rapidocr，CPU） | VLM（qwen2.5vl:7b，ollama） |
|---|---|---|
| 显存占用 | **0 MiB**（onnxruntime 只有 CPUExecutionProvider，无 CUDA EP） | **+5.13 GiB**（ollama 自报 size_vram = 5,506,041,117 B；整卡冲到 **7716 / 8188 MiB**） |
| 单帧延迟（1080x2340 整图） | **1.17 ~ 1.40 s**（中位≈1.2 s） | 独占显卡时 ~6.6 s；**与数字人共存时 179.4 s**（其中视觉编码 166.6 s） |
| 单帧延迟（只裁弹幕区） | **0.56 ~ 1.30 s**，整图/ROI 提速 1.08 ~ 2.40x | 未测（显存约束，提前终止） |
| 冷启动 | **0.28 s** 构造 + 首图 3.95 s | 4.2 ~ 10.5 s，且 keep_alive=0 后每次都要重付 |
| 中文短文本准确率 | 10 张图 GT 共 **31** 条弹幕/评论行（含 img02 的 12 条相同「接好运」）。**OCR 裁 ROI：精确命中 27、近似 3、漏检 1 → 行级召回 ≈ 92%；整图：精确命中 27、近似 2、漏检 2 → ≈ 90%** | 只有 1 张可用样本（img02），且**退化重复**（见 2.2b） |
| 输出噪声（需过滤层兜底） | 多余行多（ROI 207 / 整图 323），但绝大多数是 UI 文字：两张反例图就贡献 82 行；其余为点赞数、昵称、时间戳、卡片长文 → 见 6.2(2) 过滤规则 | 未测 |
| 与数字人(~1.0–3.1 GB)共存 | 可以，可常驻常开 | **不能**，实测触发看门狗反复重启生产链路 |

**硬约束 ≤6.6 GB 的算术结论**：VLM 单项就吃掉 5.13 GiB，留给数字人 + TTS + 桌面渲染的不足 1.5 GiB（生产数字人工作集本身约 1.0 GB）。本报告实测整卡 7716 MiB，而同项目 `docs/bench_fallback_8g_20260910_113531.md` 记录**不含 VLM 时**整卡峰值已经 7721 MiB > 6600 MiB 阈值 —— 当前链路本身已顶格，再无 5 GiB 余量。

**结论：弹幕读取走 OCR。** VLM 不作为同机候选；若将来迁到大显存卡（见 `docs/deploy_cloud_3090.md`）才重新评估。

实测过程与证据：

| 时点 | 整卡显存 | 说明 |

| 卸载后 | 回落至 **1800 ~ 1827 MiB** | 模型卸载干净，无残留 |

单图推理实测（img02，1080x2340，提示词=只输出中文文本，num_predict=384，keep_alive=0）：

| 阶段 | 耗时 |
|---|---|
| 模型加载 | 4.2 s（另一轮冷加载为 10.5 s） |
| **视觉编码 / prompt eval** | **166.6 s** |
| 文本生成 384 tok | 8.5 s |
| **合计** | **179.36 s** |

对照：同一模型、同一张图，在**显卡空载**时单图约 **6.6 s**（早前探测：视觉 token 3314 + 输出 256 token）。同一输入 **6.6 s → 179.4 s**，**27 倍降级**，根因是显存不足导致 ollama 把部分层下沉到 CPU。

模型质量侧另有一条负面证据：在密集弹幕图（img02 的 12 条 `接好运`）上，模型**退化进重复循环**，连续输出同一条直到撞满 `num_predict` 上限——这类退化输出会直接污染下游弹幕管线。

**提前终止说明**：按要求在测到 img02 后立即停止，img06 / img10 的 VLM 未执行；计划中的「VLM 喂 ROI vs 喂整图」「昵称|内容 结构化提示词」两项试验一并取消。因此**本报告不给 VLM 的准确率量化结论** —— 样本量（n=1）不足以支撑，只有在充足显存的机器上才能补齐。

## 6. 结论与选型建议

### 6.1 为什么是 OCR 而不是 VLM

1. **显存是硬门槛，不是调优问题。** VLM 一加载就是 5.13 GiB，8G 卡上数字人(约 1.0 GB 工作集)+TTS+桌面再挤进来就爆。本次实测期间生产数字人被看门狗**重启 4 次**，这是生产事故，不是「慢一点」的性能问题。
2. **共存时 VLM 会灾难性降级。** 同一张 1080x2340 图、同一个模型：显卡空着时单图 ~6.6 s；生产链路在跑时同一张图 **179.36 s**，其中视觉编码 **166.6 s**（占 93%）。原因是显存不够，ollama 把部分层下沉到 CPU。这说明「用完即卸」在 8G 卡上也不是可行折中——**每次加载都要重付 4.2~10.5 s 加载 + 可能长达 3 分钟的推理**。
3. **OCR 的显存占用恰好是 0。** 本机 onnxruntime 只有 `CPUExecutionProvider`（无 CUDA/TensorRT EP），rapidocr 全程走 CPU，**不占 1 MiB 显存**，可与数字人无缝常驻。这是本项目当前唯一能「常开」的方案。
4. **精度上 OCR 足够。** 31 条真实弹幕/评论行，裁 ROI 后精确命中 27 条、近似 3 条、只漏 1 条（行级召回 ≈ 92%）。近似的 3 条全是半遮挡/边缘截断造成的缺字（如 `阳收钱就有了根据` 左边缘被红包挂件挡住、`那么嗨免费吗?` 在 ROI 下被读成 `那么嗨！兔费嘢？`）；唯一的漏检 img08 `支持一下，期待更新` 是被抖音 Toast 整条压在下面。**这些都是遮挡问题，不是识别能力问题**，靠 ROI 框选 + Toast 检测 + 正则校验就能收敛，不需要语义模型。
   代价是**噪声行多**（ROI 207 行多余 / 整图 323 行）：OCR 会把界面上所有文字都读出来。但这是**过滤问题不是识别问题** —— 两张非弹幕反例图就贡献了 82 行，剩下的也集中在点赞数、昵称、时间戳、卡片长文这几类，用 6.2(2) 的规则可以清掉。
5. **延迟量级差一个数量级。** OCR 1.2 s/帧（裁弹幕区可到 0.6 s），足以支撑 1~2 s 一次的弹幕轮询；VLM 在共存条件下 179 s/帧，连「每 3 分钟读一次」都不成立。

### 6.2 工程建议

**(1) 一定要裁弹幕区，不要喂整图。**
实测整图中位 1.167~1.401 s，裁 ROI 后 0.560~1.298 s。更关键的是**噪声行大幅下降**：img01 输出行 41 → 16、img02 46 → 18、img04 24 → 3。整图会把状态栏、点赞数、底部导航、视频简介全读进来。
注意本报告评论面板的 ROI 取得偏大（1080x1300~1400），提速只有 1.08~1.20x；**投产时应按直播伴侣实际弹幕条带取窄 ROI（例如整屏高度的 15~25%）**，届时提速和降噪都会明显好于本报告的评论面板数字。

**(2) 噪声行过滤规则建议（按实测输出归纳）**

- **固定 UI 黑名单**：`评论[\d.万]+`、`AI 解析`、`回复`、`发送中`、`去发布作品`、`刚刚看过`、`发条评论，说说你的感受`、`分享你此刻的想法`、`点击激活`、`全屏观看`、`听抖音`、`拍同款`、`首页`、`消息`、`我`、顶部导航（`点`/`关注`/`南京`/`团购`/`商城`/`推荐`）。
- **纯数字/计量行**：`^[\d.]+万?$`（如 `143`、`2.8万`、`3.5万`、`2132`、`5396`）、以及 `共\d+人推荐`。
- **时间串**：`\d+分钟前`、`\d+小时前`、`\d{4}年\d+月\d+日`、`\d{2}-\d{2}`、`刚刚`。这类在评论/互动列表里极多（img10 里占了大半）。
- **Toast 提示**：`已将剪贴板中的内容粘贴到抖音` —— 这是抖音自己弹的提示，压在被遮住的评论上，**必须过滤**，否则会把「读不到的评论」误当内容喂进管线。
- **重复昵称行**：同一短行在连续若干行里反复出现（img10 中 `杭州众创猴科技有限公司` 连续出现 7 次）→ 判为昵称列，丢弃或单独归档为 user 字段。
- **超长行**：长度 > 25 字的行多为卡片正文（如 img06/07/08 里被完整读出的 DeepSeek V5 长文），不是弹幕 → 按行长阈值丢弃。
- **碎片行**：长度 ≤ 2 且非纯中文词的行（实测出现 `Q`、`夫`、`运`、`成`、`十`、`小`、`L`、`X`）→ 丢弃。
- **去重**：同文本在 N 秒窗口内重复只保留一条（img02 的 12 条 `接好运` 就是典型；OCR 12/12 全部读出，正好说明这是识别成功后的**去重问题**）。

**(3) 昵称/文本分离不要指望 OCR，也不值得上 VLM。**
`apps/danmaku.py` 的 `event_id_of(source, user, text, ...)` 需要 user。OCR 只能给出行文本，拿不到「哪一行是昵称」。建议用**版面启发式**：评论面板里昵称行在内容行上一行、且字号更小/颜色更浅/带 `我` 标签；若启发式不可靠，先用占位 user（如 `anon`）并把频控按 text 维度做，不要为此引入视觉模型。

**(4) 依赖与部署（需要人工确认的点）**
rapidocr 只装在 `D:\Python39\python.exe`，项目 venv `.venv-lt` 和 `C:\tools\python311` 都没有。两条路：
- 给项目 venv 补装 `rapidocr` + `onnxruntime`（**注意：本机代理 7897 已坏，pip 直连会卡死；需要先修好代理或用离线 wheel，本轮按纪律没有尝试安装**）；
- 或者把 OCR 做成**独立小进程/本地 HTTP 服务**（用 D:\Python39 跑），由链路的截图线程调用 —— 与现有架构里 ollama/tts 作为外部服务的模式一致，改动最小、且不污染项目 venv。

**(5) 已知 OCR 失效场景（如实记录）**
- 半遮挡/边缘截断会丢字：img01 `阳收钱就有了根据`（左被红包挂件挡，人眼也只能读到半句）、`级文明`（丢了开头的「一」）。
- 大字标题与弹幕重叠时会串字：img03 整图把 `GPT-6 Astra全量开放` 读成 `GPT-6 Astra全开放`、ROI 更差读成 `GPT-6 Asa全童开`；`那么嗨免费吗?` 在 ROI 里被读成 `那么嗨！兔费嘢？`。**建议对同屏大字标题区域做掩膜或把 ROI 收窄到弹幕条带**。
- 被 Toast/浮层遮挡的文本会整条漏检：img08 的 `支持一下，期待更新` 在 Toast 下面，OCR 未输出（该条 GT 由人眼补出）。
- 低对比小字（视频自带浅色字幕）在整图下会被漏：img04 整图漏了 `谁懂这份仙侠孤勇` 的背景行，但 ROI 下 2/2 全中。

**(6) 复跑命令**
```
# 完整 OCR 实测（零显存占用，可随时复跑）
D:\Python39\python.exe D:\AI\digital-human-live\scripts\bench_danmaku_ocr.py --runs 3 --skip-vlm
```
VLM 相关开关（`--vlm-keys` / `--vlm-keepalive 0` / `--vlm-runs` / `--vlm-pause`）保留在脚本里，但**在 8G 环境请勿在生产链路运行时使用**。
