# 数字人直播系统 — 日常操作手册

> 项目: `D:\AI\digital-human-live` ｜ 前置: 驱动 610.88+ / RTX 4060 8G / venv 已建好

## 一、日常启动（顺序固定）

```powershell
cd D:\AI\digital-human-live

# 1) 编排器（自动拉起 TTS 网关 + LiveTalking，等待 phase=live）
.venv-lt\Scripts\python.exe -X utf8 -m apps.orchestrator.main --profile fallback_8g

# 2) 控制台（另开一个窗口）
.venv-lt\Scripts\python.exe -X utf8 -m apps.console --profile fallback_8g
```

就绪标志：
- 编排器窗口出现 `phase=live`
- 浏览器 `http://127.0.0.1:8030` 打开控制台，状态区「数字人状态」为绿

## 二、开播流程（抖音直播伴侣 = 唯一开播入口）

1. 打开「抖音直播伴侣」，登录账号，选择场景（已配 chrome 窗口捕获）
2. 在浏览器打开 `http://127.0.0.1:8010/index.html`，点「开始连接」（数字人画面出现在该页面）
3. 伴侣中确认该 chrome 窗口有画面 → 点「开始直播」
4. 开播后在控制台核对「平台直播状态」

> 系统**不会**代替你点「开始直播」——这是设计如此（能力=MANUAL，避免误开播）。

## 三、直播中操作（控制台 8030）

| 按钮 | 作用 |
|------|------|
| 暂停讲解 / 恢复讲解 | 主话术停/续（弹幕回答仍按策略处理） |
| 停止当前回答 | 立即打断数字人正在说的话 |
| 人工接管 | 锁定自动派发；弹幕只入队不回答（pending 保留） |
| 解除接管 | 恢复自动；pending 中的明确提问会补答 |
| 人工结束场次 | 场次置 manual_end，定时器**不会**自动重启本场 |
| 立即插播 | 手动输入文本让数字人播 |
| 弹幕录入 | 把手机上看到的真实弹幕粘贴进去（manual=真实 / mock=模拟） |

## 四、下播

1. 伴侣里点「停止直播」
2. 控制台点「人工结束场次」
3. 关闭两个窗口（或 Ctrl+C），运行 `scripts\stop.ps1` 确认无残留

## 五、定时开播

控制台「直播计划」→ 填名称 / daily|once / HH:MM / 时长 → 添加（冲突自动拒绝）。
到点系统只做**预检**：编排器 live + 伴侣在运行 → 事件区提示你去伴侣点开播。
错过触发点 5 分钟以上自动跳过本场（事件区留痕）。

## 六、知识库（弹幕自动回答的依据）

控制台「知识库」→ 标题+关键词+正文(=口播回答)+来源 → 添加。
- 禁止编造价格/承诺；价格类条目必须填来源和时效
- 回答优先级：命中有效条目 > fallback 话术 > 忽略

## 六·五、声音链路（2026-09-11 排查后固化）

声音走的路径：**TTS 网关 → LiveTalking(WebRTC 音频轨) → 浏览器页面 → 直播伴侣采集 → 观众**。
任何一环断了都是"没声音"，按顺序查：

1. **服务端有没有在推音频**（命令行跑，约 1 分钟）：
   ```powershell
   .venv-lt\Scripts\python.exe -X utf8 scripts\probe_audio_path.py
   ```
   输出 `结论: ✓ 服务端确实在推送有内容的音频帧` 即服务端没问题（会给出手收到多少帧、RMS 峰值）。

2. **浏览器页面有没有在放**：打开 `http://127.0.0.1:8010/index.html` → 点「开始连接」，
   视频下方新增的**音频状态条**会显示：
   - `播放中 · 实时电平 ▮▮▮…` → 页面在放，声音是通的；
   - `浏览器拦截了自动播放` → 点它下面出现的「🔊 点这里启用声音」按钮；
   - `有声数据块 0 次` 且数字人正在说话 → 服务端没推（回到第 1 步）；
   - 有电平但听不到 → 右键标签页看是否被静音 / 查系统音量合成器里 Chrome 的音量 / 输出设备。

3. **直播伴侣要给到观众**：伴侣的**窗口捕获只有画面、没有声音**，必须在伴侣里单独开声音：
   伴侣 → 设置/声音 → 打开「**系统声音**」（把电脑播放的声音一起播出去）。
   若不想把电脑所有声音（微信、提示音）都播出去，可装 VB-CABLE 虚拟声卡：
   Chrome 输出设为 `CABLE Input`，伴侣麦克风选 `CABLE Output`，这样只有数字人的声音进直播间。

> 结论：**页面有声 ≠ 观众有声**。第 3 步不做，直播间就是无声的。

## 六·六、待机画面行为（2026-09-11 晚改版）

没有语音时，数字人**只在一小段「嘴部最安静」的画面里乒乓循环**——人仍在眨眼、点头、
身体微动（不是静止照片），但也不是"一直在讲话"的样子。有语音立刻切回正常说话。
- 自动挑选：启动时分析素材帧，取嘴部帧间差最小的 2 秒窗口（本项目素材＝帧 276~326，
  启动日志会打印 `待机段自动挑选: 帧 a~b`）；
- 手动指定/关闭：`configs/profile_*.yaml` → `livetalking.env.LT_IDLE_WINDOW`
  （`"276,326"` 指定区间，留空＝自动挑，`off` ＝恢复上游整段循环）。
- 注：源视频全片都在讲话（最长"不说话"片段仅 0.2s），所以待机只能"挑最静的窗口"，
  无法做成"专门的不说话镜头"。若以后重拍一段安静的素材，可整段替换待机窗口。
话术导演：一轮话术播完后空闲 `director.idle_gap_s`（默认 300s）才开下一轮。

## 六·七、弹幕自动接入（阶段G，OCR）

**能力**：读「抖音直播伴侣」窗口里的观众弹幕 → OCR → 弹幕管线（`source=ocr`）→ 命中知识库就自动口播回答。
不再需要人工把弹幕复制进来（人工粘贴 `source=manual` 仍然保留）。

**为什么是 OCR 不是视觉大模型**（实测见 `docs/bench_danmaku_ocr_*.md`）：

| | rapidocr（选用） | qwen2.5vl:7b（排除） |
|---|---|---|
| 显存 | **0**（CPU 推理） | **+5.13G**，8G 卡上直接把数字人挤爆 |
| 单次耗时 | 裁弹幕区后 **0.56~1.3s** | 空载 6.6s；与数字人共存 **179s** |
| 准确率 | 裁 ROI 召回 **≈92%** | 样本退化，无量化结论 |

**用法**（控制台 8030 → 实时互动（弹幕）→ 「启动弹幕OCR」）：
1. 直播伴侣保持**可见**（最小化时取不到画面，状态区会提示）；
2. 控制台点「启动弹幕OCR」→ 状态区显示 `OCR运行中 · 累计投递 N 条 · 单轮 x.xx s`；
3. 先标定 ROI（**换机器/换分辨率/换伴侣布局后必须重做**）：
   ```powershell
   D:\Python39\python.exe -X utf8 apps\danmaku_ocr.py --calibrate
   ```
   它会把伴侣窗口截图存到 `data\out\danmaku_roi.png`，**红框=当前取词区域**；
   按需改 `configs\profile_fallback_8g.yaml` 的 `danmaku_ocr.roi`（`[x,y,w,h]` 相对窗口比例）再跑一次确认。
   只框**评论列表**，不要把点赞/在线人数/礼物栏框进来（框越窄越快越准）。
4. 想先看识别效果不投递：`... --dry-run`（只打印，不进管线）。

**依赖事实**：rapidocr 3.9.2 只装在 `D:\Python39`（项目 venv 没有，pip 通道当前不可用），
所以 OCR 是**独立进程**，由控制台按 `danmaku_ocr.python` 拉起；它不占显存。

**已知限制**：
- 伴侣 UI 渲染树不可读（UIA 实测），所以只能读屏幕像素——弹幕被礼物特效遮挡时那几条会漏；
- 昵称分离是启发式（`昵称：内容`），不保证全对；回答用的是内容部分；
- 同一句 60s 内不重复投递（`dedupe_ttl_s`），改这个值会影响"观众刷屏重复提问"的行为。

## 六·八、智能问答（LLM chat，2026-09-13 接入）

两条回答路径，用途不同：

| | 知识库 FAQ（默认开） | LLM chat（默认关） |
|---|---|---|
| 回答来源 | 你录入的条目，未命中用兜底话术，**不编造** | 大模型生成，**内容不可控** |
| 适用 | 直播带货（价格/承诺必须可控） | 闲聊答疑、知识讲解类直播间 |

**开启 LLM**：
1. `configs\profile_*.yaml` 的 livetalking 段取消两行注释：`llm_provider: dashscope`、`llm_model: qwen-plus`
2. 密钥走环境变量（不入库）：`setx DASHSCOPE_API_KEY sk-xxx`，然后重开终端（orcarouter 同理用 `ORCAROUTER_API_KEY`）
3. 重启编排器（`scripts\start.ps1`）

**用法**：

```powershell
# 编排器透传（推荐, 自动带真实会话; 返回 ok=true 表示已交给 LLM 流式口播）
curl http://127.0.0.1:8020/chat -H "Content-Type: application/json" -d "{\"text\":\"用一句话介绍这款产品\"}"
```

或打开 `http://127.0.0.1:8010/dashboard.html` 对话模式直接提问（vendor 内部走 type=chat）。

说明：
- chat **不进编排器队列**（不走合并/限流），vendor 侧 LLM 生成后逐句口播；打断照常控制台「停止当前回答」（POST /interrupt）。
- 未配密钥时 chat 返回上游失败（如实报错），知识库与插播路径不受影响。
- 带货场景慎用：LLM 可能编造价格/承诺，直播间对外承诺一律走知识库条目（带来源+时效）。

## 六·九、声音克隆（CosyVoice zero_shot）

1. 准备参考音频：wav、单声道、3~10 秒、环境干净、内容清晰，存为 `data\voices\my_clone_ref.wav`
2. `configs\voices.yaml` 取消 `my_clone` 段注释；`ref_text` 必须**逐字**填参考音频说的话
3. `configs\profile_*.yaml` 的 livetalking 段把 `REF_FILE: default` 改为 `REF_FILE: my_clone`
4. 重启编排器生效；先离线验证再开播：

```powershell
curl http://127.0.0.1:8011/v1/audio/speech -H "Content-Type: application/json" -d "{\"input\":\"测试克隆音色\",\"voice\":\"my_clone\",\"response_format\":\"wav\",\"speed\":1.0}" -o logs\clone_test.wav
```

提示：参考音频路径解析已按 voices.yaml 注释口径修复（2026-09-13：旧实现剥文件名拼到
data\ 根，按示例放 data\voices\ 会报"参考音频不存在"）。

## 六·十、控制台诊断面板与"多标签页抢声音"（2026-09-13）

控制台（8030）新增三块：

1. **智能问答（LLM chat）**：输入问题 → 编排器 /chat 透传大模型流式口播。
   面板会显示是否已启用（provider/model）及开启方法。
2. **声音与会话面板**：显示当前绑定的 sessionid、vendor 活跃会话数。
   - 活跃会话 >1 → 红字警告（有多余标签页在分走声音）；
   - 绑定消失/failed → 红字提示去 8010 页面点「开始连接」。
3. **声音链路自检按钮**（约 1 分钟）：跑 `scripts\probe_audio_path.py`——用与浏览器
   页面完全相同的 WebRTC 方式连上 LiveTalking，派发测试句并统计收到的音频帧与 RMS：
   - `✓ 服务端确实在推送有内容的音频帧` → 问题只可能在浏览器播放/系统音量/伴侣采集（按六·五查）；
   - `✗ 一帧音频都没收到` → 服务端 WebRTC 链路问题（找开发，不是你的操作问题）；
   - `△ 收到音频但全是静音` → TTS→口型的音频内容为空（查 tts.log）。

**"多标签页抢声音"已修复**（2026-09-13，"循环话术没声音修了好几遍"的元凶之一）：
旧逻辑每次派发前都无条件改绑"最新创建的会话"，只要多开一个标签页
（dashboard.html、第二个 index.html，甚至后台忘了关的测试页），绑定几秒内被抢走，
声音去了没人监听的页面；关掉多余标签又"自己好了"。现在改为**粘性绑定**：
当前会话活着绝不换，只有它真正消失（页面刷新/断开）才收养最新会话，重绑会落日志。
直播时仍建议只保留一个 8010 页面。

## 七、常见故障

| 现象 | 处理 |
|------|------|
| 编排器 phase=failed | 看 `logs/orchestrator.err.log`；常见是端口占用→`scripts\stop.ps1` 后重启 |
| 数字人没声音 | 按「六·五 声音链路」三步走；先跑 `scripts\probe_audio_path.py` 定位是哪一段 |
| 页面一直动嘴没声音 | 正常——那是待机动画；播一遍后会定格 5 分钟（见「六·六」） |
| 数字人反复重启 | 看 `logs/orchestrator.out.log` 的 watchdog 行：`vram_exceed` 才是本链真的超了；<br>`vram_total_high` 只是整卡被别的程序占满（只告警不重启）。本链口径用 `scripts\gpu_owned_query.ps1` 单独查 |
| 弹幕OCR 没反应 | 控制台弹幕区看 OCR 状态：窗口最小化/标题不含"直播伴侣"/ROI 框错都会写明；日志 `logs\danmaku_ocr.log` |
| TTS 进程被杀 | 看门狗 70s 内自动拉起；连续 10 次失败会熔断转人工 |
| 数字人画面卡 | 看 `logs/livetalking.log` 的 infer fps <20 → 看门狗会重启口型进程 |
| 缓存话术没生效 | 文本/音色/语速任一变了都会重新合成（首次 10-20s，之后 0s） |
| 显存 >6.6G | 看门狗自动降级/重启；仍超就关掉多余 Chrome 标签页 |
| 温度 >75℃ | 降负载（关预览页多余标签），不要超频 |

## 八、性能事实（本机实测）

- 口型推理 55~66fps；接收端稳定 25fps
- CPU TTS 首句合成 10~19s（RTF>1，不流式）；**缓存命中 0s**
- 显存 3.1G/8.2G @48℃（fallback 档，不含 OBS）
- 弹幕回答：缓存命中常见问题 P95 < 2s；新问题（CPU合成）P95 > 10s——**新问题实时回答未达标，依赖预缓存**
